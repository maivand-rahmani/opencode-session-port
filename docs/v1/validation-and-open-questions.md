## 2. Tested evidence (what was observed)

- **E1.** A TUI plugin can call `context.client.session.import({ info, messages, location })` through the host-provided client. The call maps to `/api/experimental/session/import`, which is Experimental-only — a significant API-compatibility risk. The TUI public plugin context does not expose server URL/auth, so a subprocess cannot reliably target the same host server. Direct database writes are excluded from the design. Status note (2026-10-09, E27 limits): this runtime observation is contested by tagged/installed plugin `SessionDomain` type declarations that omit `import`, conflicting with the generated-client observations — the actual installed plugin context surface has not been re-verified; unresolved open issue (see §3). V1 policy (owner decision 2026-10-10 — O-12): at `/restore` start, check whether `context.client.session.import` is callable before reading or decrypting the artifact; if absent, show a clear message that the required capability is unavailable and no sessions were changed, then stop. Policy only — the actual installed `context.client` surface is bounded-verified on one host: the bounded O-19 probe (E32) made no `context.client` calls and does not validate the import API, but the later bounded actual-TUI client probe (`fix-49`; E33, 2026-10-10) observed `typeof ctx.client.session.import === 'function'`, callable `session.get`/`message.list`, and exactly one synthetic public-client import succeeding and reading back on one Windows v2.0.22 host (one import, no retry). Broader versions/platforms, the concrete product probe implementation, and the product `/restore` fail-early behavior remain OPEN (OQ-12; not implemented); the contested declaration mismatch is bounded-addressed at runtime on that one host only.
- **E2.** The import call created a synthetic child session referencing an existing parent. The TUI session-list cache included the imported session ID (observed once).
- **E3.** Importing with a repeated (already existing) session ID returned `ConflictError`; the original session title was unchanged.
- **E4.** Synthetic user and assistant text messages imported and read back through `client.message.list({ sessionID })`.
- **E5.** In the v2.0.22 transfer format, messages carry inline content; there is no separate parts array or part ID. (Tool content is inline within assistant message content.)
- **E6.** Reusing a message ID in a different session caused HTTP 500. Verification showed the attempted new session and its messages did not exist afterward — no partial session in this single tested collision. This must not be generalized to other failure modes or API errors. Status update (2026-10-09, E27): the disposable host probe observed HTTP 500 for message-ID reuse within and across sessions, with no target session/messages observable afterward via public reads; absence was observable through public reads only — not proof that imports are transactional.

- **E21 (gzip boundary source review; RFC 1952 §2.2; `lib-19`; bounded; no new runtime test).** RFC 1952 §2.2 permits concatenated gzip members but states there is no additional information after the compressed data; zero padding is not required by the format. Ordinary Node/Bun stream APIs and `bytesWritten` do not reliably prove exact input consumption, so they cannot by themselves establish whether trailing bytes are consumed or ignored. The E20 observation that trailing zero bytes (1–16) are silently ignored is specific to the tested Bun 1.3.10/zlib build and must not be generalized. Consequence: the owner decided the boundary policy on 2026-10-09 — accept one or more complete gzip members and reject any bytes after the final member, including zero padding (decision-log `fix-20` entry); strict end-of-input validation is required before plaintext is released; the decoder implementation is owner-selected and complete/tested (`fix-25`; E26; Oracle `ora-22` GO scoped to implementation correctness only), while host-runtime and cross-runtime/portable validation remain OPEN (not complete), because ordinary stream APIs and `bytesWritten` do not reliably prove exact input consumption.

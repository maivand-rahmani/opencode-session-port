# SessionPort V1 — Technical Design

> **APPROVED FOR IMPLEMENTATION — NOT FROZEN.**
> This is the owner-approved implementation baseline; PROPOSED/OPEN choices remain subject to phase gates. Baseline: OpenCode v2.0.22 (2026-10-09). Source references are pinned to the OpenCode repository tag `v2.0.22` unless noted. Decision status is authoritative in [decision-log.md](decision-log.md).

## 1. Scope

How SessionPort would produce checkpoints, move them via user-operated Git, and restore them into an OpenCode environment. Semantics marked DECIDED come from the product decision log; implementation choices are PROPOSED or OPEN.

## 2. Architecture (PROPOSED)

Components:

1. SessionPort plugin running in the OpenCode TUI with the host-provided plugin context.
2. Host-provided generated client (`context.client`) used for all session operations.
3. Checkpoint artifact: a single encrypted file. The user transports it with Git (or any channel); SessionPort never runs Git.
4. OMO Slim adapter: V1 is a no-op with no OMO-specific transfer (DECIDED — P-14; §7).

Anti-choices (DECIDED direction):

- No direct writes to OpenCode database files.
- No plugin-spawned CLI (`opencode session import ...`) targeting the host server by default (see §3, E8-type constraint).
- No LLM/model calls; no replay of historical tools.

### 3.1 Declaration/source research (pinned v2.0.22 tag; not runtime-tested)

Recorded 2026-10-09 (Phase 2 research). These items come from tagged v2.0.22 API declarations and source reading, not from executing a host; declarations and implementation observations are labeled. No new host runtime or platform tests were run.

- **Session listing (`GET /api/session`).** Declared filters: `directory`, `project`, optional `subpath`, `search`, `parentID`; declared default page limit 50; cursor pagination with no total/hasMore; no snapshot-consistency guarantee is documented. Project + `subpath` define the scope; there is no worktree parameter. Source observation: the list implementation does not exclude archived sessions. Bounded runtime observation (2026-10-10, E37; `fix-59`; one isolated actual Windows OpenCode v2.0.22 TUI plugin runtime; public `ctx.client` only; synthetic): one `session.list({project: <host-assigned target projectID>, limit: 50})` response returned three imported synthetic descendants (parent→child→grandchild) exactly once with hierarchy intact, and `parentID` filters returned the exact direct child/grandchild; the response carried non-null `cursor.previous`/`cursor.next`. One host/run only — no cursor traversal/exhaustion, archived-flag, root/`parentID=null`, other-filter, failure/consistency, or other-version/platform/restart behavior was tested; enumeration completeness/P-03 is not established (runtime semantics remain OPEN — OQ-10; O-21 stays OPEN). Bounded addendum (2026-10-10, E38; `fix-61`; one isolated actual Windows v2.0.22 TUI plugin runtime; public `ctx.client` only; synthetic): a single `session.list({project, limit: 2})` traversal over four imported synthetic sessions (parent→child→grandchild plus an independent root) returned page 1 = 2 entries, page 2 = 2 entries, page 3 = 0 entries, terminating at null `cursor.next` with each of the four IDs exactly once; `session.archive` was absent (undefined/undeclared) on this installed client — no archive call was made, and a declared `info.time.archived` timestamp being imported, read via `session.get`, and listed is not archive-API evidence — bounded to that host/client. One host/run and synthetic imports only: no generic pagination-completeness, archive-API, snapshot-consistency, cross-version/platform/restart, or O-10-closure claim; enumeration completeness/P-03 is not established and pagination/exhaustion semantics beyond this single traversal remain untested (runtime semantics remain OPEN — OQ-10; O-21 stays OPEN). Archived-session inclusion policy is decided (owner, 2026-10-10): archived sessions returned by the project-scoped listing are included with no extra `time.archived` filter — with no claim that all runtimes return archived rows or that every archived session is accessible, and E38 remains one synthetic record on one run.
- **`Session.Info`.** Declares `parentID?`, `fork?: { sessionID, boundary }`, and project/location metadata; there is no children array, so children must be resolved by filtering. Transfer requires the parent session to exist before a child import.
- **Message listing.** Declared: default page size 50, cap 200, default order `desc`; supports `order`, cursor, and type filtering, but `order` cannot be combined with cursor; a type filter (if used) must be preserved across cursors, and omitting it preserves all types. The message union includes all message types and assistant tool content. Implementation-derived: messages are ordered by stored sequence; exact cursor details are implementation-specific. No consistent-snapshot guarantee is documented. Message-to-session association is endpoint-scoped: `SessionMessage.Info` variants declare no `sessionID` field, and `GET /api/session/:sessionID/message` (the route behind `context.client.message.list(sessionID)`) scopes the response and filters messages by the route parameter (E18; bounded source research, not runtime-tested).
- **Transfer schema and filtering.** Payload schema: `{ info: Session.Info, messages: SessionMessage.Info[] }`. Source behavior: official export/import filters unsettled messages — an assistant message without a completion time and a running shell/compaction are unsettled. Because completeness is DECIDED (P-05), the checkpoint fails closed on this condition instead of silently filtering (see §4 step 4).
- **ID schema constraints and import ID handling (bounded source research; not runtime-tested).** `SessionID` validation requires only the `ses` prefix and `SessionMessage.ID` only the `msg_` prefix; no suffix length, alphabet, or uniqueness constraints are declared. Generated IDs conventionally append a 26-character ascending identifier after `ses_`/`msg_`, but that form is generator convention, not a schema requirement and must not be required. Import source uses supplied session and message IDs; the tested HTTP path read back the supplied session ID. Still unverified by source research: arbitrary deterministic suffixes, message-ID preservation, and collision behavior (the only tested collision remains the HTTP 500 case in §3); no explicit message-ID import duplicate/collision branch was identified in source. Status update (2026-10-09, E27 runtime probe — see §3 note): arbitrary IDs matching the `ses`/`msg_` prefixes (including punctuation/case variation) imported and read back verbatim; re-import → 409 with the existing record/messages unchanged; message-ID reuse within/across sessions → HTTP 500 with no target session/messages observable via public reads; invalid later message → 400 with no observable partial session (one Windows v2.0.22 headless server; public API only). The O-22 scheme (owner-selected for implementation 2026-10-09) selects `ses_`/`msg_` + 64 lowercase hex; host acceptance of that exact supplied-ID shape is bounded-verified by the separate E28 probe (`fix-30`; one isolated Windows v2.0.22 headless server; 6/6 exact import/read/export checks; supplied IDs only; E33 adds bounded exact-shaped readback through the actual TUI client), while SessionPort's BLAKE2b derivation, derived-ID collision behavior, related-session/fork references, parent/child/fork cases, cross-platform behavior, and general transactional semantics remain unverified; plugin `context.client` availability is bounded-verified on one actual TUI host only (E33). See §5 step 8 and O-22/OQ-24.
- **Import `location`.** Declared as a target public location; implementation observation: when omitted, the destination defaults to the server cwd. The design always sets the destination explicitly and never derives it from the source session's `info.location` — V1 policy resolved (owner decision 2026-10-10): always supply an explicit import target location; accept host-assigned target project scope; do not promise to preserve the source `info.projectID`/`info.location`; runtime claims stay bounded to E31/E33. Actual host mapping/runtime scope behavior remains OPEN (OQ-16). Bounded observations: E28 saw one import replacing a supplied `projectID` with a location-derived ID; E31 (`fix-42`; one isolated authenticated Windows v2.0.22 loopback headless server; public API only; four synthetic imports) saw explicit targets A/B produce distinct target-scoped project IDs with `location.directory` matching the explicit target, the same target return the same project ID despite differing supplied `info.projectID`/`info.location` values, and supplied values absent from readback. These are single-probe observations only: no project-ID hash/algorithm or cross-restart stability inference and no supplied-`projectID` preservation implication; actual host destination/location mapping and scoping remain OPEN (OQ-16; runtime validation), and omitted `location`, relative paths, conflict/reimport, cross-server/restart/platform, and broader TUI `context.client` behavior remain untested. A later bounded actual-TUI client probe (E33, `fix-49`, 2026-10-10; one run) observed one synthetic public-client import preserving the explicit target `location.directory` and a host-assigned projectID distinct from the supplied `info.projectID`/source `info.location` — one-run TUI observation only; no general location/project-ID semantics.

- **Project mapping fields (bounded source research; `lib-31`, 2026-10-10; not runtime-tested).** Pinned v2.0.22 `Project` carries `{id, canonical, sandboxes}`. Source reading indicates `canonical` can be another clone/main-checkout of the project; it is not guaranteed to be the current/only/existing target, and importing to the canonical directory does not guarantee reproducing that listed project ID. Consequence: the destination pair (host project ID + canonical directory) must be resolved unambiguously at runtime and the restore must fail closed before any import if it cannot; `canonical` must not be assumed stable, unique, or current. OQ-16 runtime pair validation remains OPEN.

Design constraints derived from the environment:

- The TUI public plugin context does not expose server URL/auth, so a subprocess cannot reliably target the same host server. The direct client method is the tested path.
- The official `opencode session import <file> --directory <dir>` CLI exists, but the plugin cannot safely obtain the host URL/auth needed to direct a spawned CLI at the TUI's current server. The subprocess route is excluded from this V1 design; revisit only if OpenCode exposes a safe host mechanism.

No snapshot consistency is documented; concurrent-mutation behavior is OPEN (O-21/OQ-23).
2. Children/subagents are included via the project-scoped listing itself; no separate descendant query or filter is added (owner answer 2026-10-10: the set is every entry returned by exhaustive pagination). `parentID`/`Session.Info` relationships are used for ordering/reporting (no children array is declared); the exact child-association rule and `fork` semantics remain OPEN (OQ-10).
3. Empty result set → notify and stop; no artifact (DECIDED).
4. Build the payload: each session's info plus all its messages (`{ info, messages }` transfer shape). Messages are bound to a session by the scoped message-list endpoint, not by a per-message ownership field — v2.0.22 `SessionMessage.Info` declares no `sessionID` (E18; runtime validation remains OPEN). "Complete/no truncation" is DECIDED and means all sessions are written or the checkpoint fails with a clear error — never a silently truncated or partial artifact. Fail-closed rule (derived from P-05): if any enumerated message is unsettled under official transfer/import filtering and would be dropped (for example, an assistant message without a completion time, or a running shell/compaction), stop with a clear error and emit no artifact — never silently filter.
5. Serialize as JSON. Duplicate comparison is defined over the canonical JSON of the complete `{info,messages}` payload (object keys sorted only; all values, array order, IDs, and absent-vs-null preserved) — owner-approved 2026-10-09, O-04 resolved. Artifact identity and remapped-ID derivation are owner-selected for implementation (2026-10-09, O-22): generate one random 128-bit artifact identity per checkpoint artifact and authenticate it in the artifact; derive IDs with BLAKE2b-256 over a versioned, namespace-separated, unambiguously length-prefixed tuple containing artifact identity and original ID; encode as `ses_`/`msg_` + 64 lowercase hex. The same artifact identity/namespace/original ID derives the same output; separately created checkpoints are distinct even for identical payloads. Exact authenticated-field placement and envelope layout remain provisional under O-02; runtime validation remains OPEN (OQ-24).
6. Compress the payload with streaming gzip (DECIDED: compression before encryption).
7. Prompt for the password twice and require the entries to match, with strength guidance shown as advisory only (no strength-based rejection); encode the password string as UTF-8 with no Unicode normalization; masked paste is allowed; on confirmation mismatch, clear both fields, show a neutral mismatch message, and retry the two-entry prompt until match or cancel; V1 password entry is interactive-TUI-only — no password CLI argument, environment-variable, or stdin/batch channel (owner subdecisions 2026-10-10; P-13/O-07 — O-07 remains OPEN only for exact case-level coverage, clipboard-write behavior, product integration, and lifecycle requirements not explicitly established; a bounded actual-host probe now exists (E41, 2026-10-10; `fix-69`: four runs — two clean with DEBUG off/on and two disclosed development runs; input injection and frame/log capture completed; all four reported target cases exercised but not enumerated, so the case-to-requirement mapping is unavailable and individual behavior/lifecycle validation is not established; zero raw-secret hits across captured frames, stdout/stderr, console cache, saved DEBUG log, and a full-root file scan; SHA-256 byte equality between typed/pasted secrets and accepted bytes; baseline restored, temp artifacts/root cleaned; the report specifies no exact host/runtime versions — bounded observations only, not a general host guarantee); bounded input-surface research/prototype evidence — E34, 2026-10-10 — shows stock OpenTUI 0.5.14 input renders its real value and DEBUG logging may include plaintext text-node values; ### Artifact envelope direction (PROPOSED; all field details, bounds, and sizes OPEN)

Recommended direction: a versioned binary envelope written as an authenticated stream.

- **Header:** magic bytes + format version + explicit compression/KDF/cipher identifiers + bounded parameters, including an Argon2id profile identifier.
- **Allow-listed profiles only:** the header references a fixed Argon2id profile table; artifacts cannot inject arbitrary KDF work values, and unknown profiles are rejected before any KDF work.
- **Profile read semantics (owner-approved 2026-10-09 — T-10):** `create(policy)` selects the profile used to seal new artifacts; `openAndStage` may open any profile code present in the factory's explicitly supplied allow-list, not only the seal-time profile; unknown/absent profile codes are rejected before KDF. The runtime policy registry is intentionally empty — no production profile or parameter values are selected (O-01/O-03) and the envelope remains PROPOSED/not frozen (O-02).
- **Per-artifact random salt** for the password KDF.
- **Per-artifact identity:** one random 128-bit identity generated once per checkpoint artifact and authenticated in the artifact (owner-selected for implementation 2026-10-09; O-22), used as the stable input for deterministic remapped-ID derivation (`ses_`/`msg_` + 64 lowercase hex via BLAKE2b-256 over a versioned, namespace-separated, unambiguously length-prefixed tuple of artifact identity and original ID). Exact authenticated-field placement and envelope layout remain provisional (O-02); host acceptance of the exact 64-hex supplied-ID shape is bounded-verified by the separate E28 probe (`fix-30`; one isolated Windows v2.0.22 headless server; 6/6 exact import/read/export checks), while SessionPort's provisional derivation implementation has synthetic unit-test and scoped Gate 3 evidence (E29), but remains host/runtime-unvalidated (OQ-24).
- **Secretstream header** for XChaCha20-Poly1305 `secretstream`.
- **Length-framed ciphertext chunks**; security-relevant header/framing fields are authenticated as AEAD additional data (AAD).
- **Final tag required:** a valid secretstream final tag must be present and verified; truncated streams fail closed rather than yielding partial plaintext.

Fail-closed properties: the header must be small, bounded, and fully validateable before any KDF work; unknown format version or algorithm → reject before KDF and before any decryption attempt, with no silent substitution; ciphertext-size, decompressed-size, and expansion-ratio caps are enforced (streaming where possible) and over-cap artifacts are rejected before import; no arbitrary archive path extraction — the payload is parsed in memory from authenticated plaintext and never extracted as files. Exact caps, profile values, and chunk/frame and salt sizes are OPEN and require benchmarking (OQ-21). A provisional implementation of this envelope exists and passes synthetic unit tests on Bun 1.3.10/Windows (E19/E20); it is not frozen and has no production profile or caps.

## 5. Restore data flow (steps PROPOSED; semantics DECIDED where noted)

1. Read the artifact file (size caps enforced).
2. Parse and validate the header and identifiers against the allow-lists; reject unsupported/unknown parameters before any KDF work; no fallback to a different KDF/cipher.
3. Prompt for the password (DECIDED entry: plugin-owned custom masked TUI modal — P-13; owner subdecisions 2026-10-10: UTF-8 encoding with no Unicode normalization and up to three failed password attempts per command run; masked paste is allowed; V1 password entry is interactive-TUI-only with no password CLI argument, environment-variable, or stdin/batch channel; O-07 remains OPEN only for exact case-level coverage, clipboard-write behavior, product integration, and lifecycle requirements not explicitly established (bounded actual-host probe evidence now exists — E41, 2026-10-10; `fix-69`: four runs — two clean with DEBUG off/on and two disclosed development runs; input injection and frame/log capture completed; all four reported target cases exercised but not enumerated, so the case-to-requirement mapping is unavailable and individual behavior/lifecycle validation is not established; zero raw-secret hits across captured frames, stdout/stderr, console cache, saved DEBUG log, and a full-root file scan; SHA-256 byte equality between typed/pasted secrets and accepted bytes; baseline restored, temp artifacts/root cleaned; the report specifies no exact host/runtime versions — bounded observations only, not a general host guarantee); bounded input-surface research/prototype evidence (E34, 2026-10-10) shows stock OpenTUI 0.5.14 input renders its real value and DEBUG logging may include plaintext text-node values — raw password text must stay out of rendered/reactive nodes and logs, and this remains only partially runtime-verified (bounded E41 runs; no per-case coverage); no reliable component/test-renderer leakage test is currently established (E36, 2026-10-10: OpenTUI `testRender` under Bun's normal test condition rendered the modal but its `useKeyboard` hook did not subscribe — mock key input only reached OpenTUI's Ctrl-C handler — and an exploratory browser-condition run captured frames that did not update consistently; the incomplete test was removed; actual TUI input, frame, event/log, and DEBUG-on/off leakage tests remain OPEN for exact case-level coverage and the other residuals)); derive the key using the Argon2id profile referenced by the validated header and the per-artifact salt. Any profile in the explicitly supplied allow-list may be opened (T-10); a code outside that allow-list is rejected before KDF.
4. Authenticate and decrypt the streamed ciphertext (XChaCha20-Poly1305 `secretstream`), verifying every chunk and the final tag; failure → stop with nothing imported.

# SessionPort V1 — Security and Privacy

> **APPROVED FOR IMPLEMENTATION — NOT FROZEN.** The crypto suite remains PROPOSED and unvalidated; see [decision-log.md](decision-log.md).
> Baseline: OpenCode v2.0.22 (2026-10-09). Decision status is authoritative in [decision-log.md](decision-log.md).

## 1. Protection scope (DECIDED)

Encryption protects one thing: **the checkpoint artifact at rest** — the file on disk, in the Git working tree, and as committed objects — against readers who do not hold the password. Everything else is out of scope by design or still unresolved.

## 2. Explicit non-protections

- A compromised or instrumented endpoint (malware, keylogger, debugger, modified OpenCode/SessionPort runtime) can observe passwords and decrypted data.
- Decrypted material exists in memory during checkpoint/restore. Bounded memory handling is hygiene, not a security boundary; there is no secure-deletion promise, only best-effort clearing.
- No author authenticity: anyone with the password can produce a valid artifact. Encryption shows possession of the password, not identity.
- Git metadata/history is untouched: commit messages, author names, timestamps, artifact filenames, and prior artifact revisions remain. Old ciphertext versions stay unless the user rewrites history.
- No secret detection or redaction: sessions can contain prompts, tool output, absolute paths, tokens, or credentials. SessionPort does not scan or remove them.
- Resource exhaustion beyond enforced limits, side channels, and traffic/metadata analysis are out of scope.
- Host-side debug logging: the OpenTUI Solid reconciler debug logger may include plaintext text-node values when DEBUG is enabled (bounded research finding, E34; not runtime-verified; E36, 2026-10-10: no reliable component/test-renderer leakage test is currently established — actual TUI DEBUG-on/off leakage tests remain OPEN for exact case-level coverage; a bounded actual-host probe (E41, 2026-10-10; `fix-69`: four runs — two clean with DEBUG off/on and two disclosed development runs; input injection and frame/log capture completed; all four reported target cases exercised but not enumerated, so the case-to-requirement mapping is unavailable and individual behavior/lifecycle validation is not established; zero raw-secret hits across captured frames, stdout/stderr, console cache, saved DEBUG log, and a full-root file scan; SHA-256 byte equality between typed/pasted secrets and accepted bytes) observed no raw-secret leakage in those bounded runs; the report specifies no exact host/runtime versions). SessionPort's requirement is to keep raw password text out of rendered/reactive nodes and logged state; that property is not yet proven generally (the bounded E41 runs observed zero raw-secret hits).
- Do not call any artifact "secure." Encryption strength depends on the pending validation of the PROPOSED suite in §5 (KDF profile values, limits) and on the user's password.

## 3. User-facing warnings (to surface in product UX)

- Treat every artifact as sensitive.
- Password loss is unrecoverable — there is no recovery or escrow path.
- Anyone with both repository access and the password can read the contents; repository access alone yields ciphertext.
- Sessions may contain sensitive content; review before committing or pushing artifacts into any repository, private or otherwise.
- SessionPort is not a compliance or secret-management tool.

## 4. Password handling

**DECIDED:** mandatory encryption; the password is never stored with the artifact or repository; no recovery; no plaintext fallback; no plaintext temp-file design; loss means permanent inaccessibility.

**DECIDED (P-13, 2026-10-09):** entry uses a plugin-owned custom masked Solid modal rendered in the TUI via `context.ui.dialog.show` (OpenTUI `Input` and OpenCode `DialogPrompt` have no mask mode). Not a host security guarantee: the secret remains in plugin-process memory. The password must never be logged, persisted, or written to the clipboard; it is masked at all times and the fields are cleared on cancel/unmount. A bounded actual-host probe exists (E41, 2026-10-10; `fix-69`: four runs — two clean with DEBUG off/on and two disclosed development runs; input injection and frame/log capture completed; all four reported target cases exercised but not enumerated in the completion report, so the case-to-requirement mapping is unavailable and individual typing/edit/paste/cancel/unmount behavior, the "no rendered frame contains the raw value" invariant, and lifecycle validation are not established; the probe's supported observations are limited to zero raw-secret hits across captured frames, stdout/stderr, console cache, saved DEBUG log, and a full-root file scan, plus SHA-256 byte equality between typed/pasted secrets and accepted bytes; baseline restored, temp artifacts/root cleaned, repository untouched), while exact case-level coverage, clipboard-write validation (the report does not state it), product integration, lifecycle requirements, and exact host/runtime versions remain unestablished. Bounded input-surface research (2026-10-10, E34; `lib-27`/`ora-25`): official OpenTUI 0.5.14 `InputRenderable` exposes no password-mask API and stock input renders its real value — frames can expose plaintext; the OpenTUI Solid reconciler debug logger (`packages/solid/src/reconciler.ts`, `packages/solid/src/utils/log.ts`) may include plaintext text-node values when DEBUG is enabled. ## 5. Cryptographic direction

**DECIDED requirements:**

- Authenticated encryption (AEAD) with a password-based key derivation function (KDF).
- Compression applied before encryption.
- Authenticity verified before parsing or importing any payload.
- Bounded header parameters validated before any KDF execution.
- Unknown format versions and algorithms rejected.
- Artifact size and decompressed-size limits enforced (resource exhaustion / decompression-bomb mitigation).
- No arbitrary archive path extraction; no writing payload-derived files.

**OPEN:** final validation of the proposed suite; Argon2id profile values (ops/memory); chunk/frame and salt sizes; KDF resource caps; ciphertext/decompressed-size/expansion caps; pinned libsodium package version and packaging/`sodium.ready` initialization compatibility (O-19; the pinned `libsodium-wrappers-sumo@0.8.4` JS builds embed ~285 KB WASM and instantiate it — no standalone `.wasm`, corrected 2026-10-10 by E35; `sodium.ready` is verified only in the one bounded E32 setup runtime — one run, junction-based resolution, no `context.client` calls — while packaging/bundling and the wider runtime matrix remain unvalidated). A bounded interactive KDF timing run exists (E35, 2026-10-10: 2 ops/64 MiB, n=15, median 125.6 ms/p95 144.3 ms on one Windows dev host) but its ~272 MiB process peak exceeded the required 128 MiB process-wide cap, so it is noncompliant/diagnostic and does not fix any profile or cap. Password encoding/normalization is owner-decided (UTF-8, no Unicode normalization — 2026-10-10; P-13/O-07) and is not OPEN. Final parameters must not be written until validated and benchmarked on the project runtime matrix. Owner process (2026-10-10): no crypto profile/value, format freeze, or cap is chosen; the owner authorizes an evidence-backed, reviewed proposal only after establishing the min-spec hardware/runtime matrix, KDF latency ceiling, and memory ceiling, with profile/format/resource candidates presented for owner approval. The production registry remains empty and no artifact commands are enabled yet. Owner planning answers (2026-10-10): the exact minimum device/runtime floor for Windows/macOS/Linux will be specified by the owner and KDF benchmarks await that floor; 500 ms p95 is a KDF measurement review target only; memory measurement must record process-wide peak and incremental/plugin-attributable peak, with the numeric product memory ceiling deferred until those measurements and rationale are reviewed.

**PROPOSED direction (recommended; NOT final, NOT validated):** a pinned libsodium implementation — `libsodium-wrappers-sumo@0.8.4` (JS builds embed ~285 KB WASM and instantiate it; no standalone `.wasm`; corrected 2026-10-10 by E35) — providing the libsodium Argon2id password KDF (`crypto_pwhash`, random per-artifact salt) and XChaCha20-Poly1305 `secretstream` for authenticated ordered chunks, applied to a streaming-gzip (RFC 1952) compressed payload. The versioned envelope carries explicit compression/KDF/cipher identifiers and an allow-listed Argon2id profile (artifacts cannot supply arbitrary KDF work values), plus the secretstream header and length-framed ciphertext chunks; security-relevant header/framing is authenticated as AAD, and a valid final secretstream tag is required. Unsupported version/profile/algorithm is rejected — there is no silent fallback to a different KDF or cipher.

Rationale (not a security guarantee): one pinned implementation to package; `secretstream` is designed for streaming authenticated chunk sequences with a final tag; Argon2id is memory-hard and specified in RFC 9106. This is not a claim that the suite is "most secure" in any universal sense; it is a recommendation pending validation.

**Evidence status:** the libsodium.js project documents WASM build variants and Node/Bun compatibility (project-level documentation; the pinned `libsodium-wrappers-sumo@0.8.4` package used here embeds ~285 KB WASM in its JS builds and instantiates it — no standalone `.wasm`; corrected 2026-10-10 by E35). Phase 1 synthetic tests under Bun 1.3.10 on Windows exercised the ESM default import + `await sodium.ready`, libsodium Argon2id at the library's absolute minimum OPS/MEM limits (test-only — **not** a production profile), a two-chunk `secretstream` round trip with a required final tag, primitive-level rejection of a wrong key, tampered ciphertext, and tampered header, and an in-memory `node:stream`/`node:zlib` gzip round trip with no filesystem use. These ran outside the OpenCode TUI plugin runtime; the plugin's ability to package and initialize the pinned package (JS builds embed ~285 KB WASM; `sodium.ready` includes embedded-WASM loading/instantiation — E35 correction; one bounded run per E32), the artifact container/framing/AAD design, production parameters/caps, and all cross-platform behavior remain **untested**, and the suite is still not a final, production-validated design. The earlier TUI plugin-loader smoke attempts (2026-10-10, `fix-40`) produced no runtime result — neither plugin setup nor `sodium.ready` was established in that attempt (validation doc E30, historical). A later bounded one-run probe (`fix-47`; E32) established plugin setup and `sodium.ready` in one Windows actual OpenCode v2.0.22 TUI plugin setup runtime (`libsodium-wrappers-sumo@0.8.4` resolved via a junction from plugin-local `node_modules` to repository `node_modules`; no `context.client` calls), while packaging/bundling and the wider runtime matrix remain unvalidated. Runtime caveats: crypto functions are reached via the ESM default object (not runtime named exports despite declarations); secretstream state representation differs between generated typings and runtime, so callers must not depend on it. For pinned `libsodium-wrappers-sumo@0.8.4`, public docs/declarations provide no state-release helper; release application references, but do not claim the underlying state is explicitly freed. Only SessionPort-owned buffers are best-effort memzeroed. Do not import current `master`'s `sodium.free(state)` guidance into this pin. References for research only: libsodium documentation — `crypto_secretstream_xchacha20poly1305` (secretstream) and `crypto_pwhash` (Argon2id password hashing); libsodium.js project documentation (including its WASM build variant; Node/Bun compatibility); RFC 9106 (Argon2); RFC 1952 (gzip). Exact pins/versions remain OPEN (O-01, O-19).

## 6. Untrusted artifact handling (DECIDED direction; details OPEN)

- Treat artifacts from other machines/checkpoints as untrusted input; assume adversarial.
- Validate header/structure and bounded parameters before expensive operations.
- Authenticate before parse/import; reject on failure or ambiguity (fail closed).
- Corrupt core data → reject before any import (product decision; owner decision 2026-10-10, O-11 resolved): the entire artifact fails before any import on any invalid payload/authentication, UTF-8/JSON, schema/root/unknown-field, reference, or planner error; no salvage or partial data. Strict fail-closed policy; no statement that all artifacts are validated in runtime.
- No filesystem extraction; no execution of payload content.

## 7. Threat boundary summary

| Scenario | Status |
| --- | --- |
| Reader without password accesses the artifact at rest | Intended protection, subject to crypto choices and password strength |
| Reader with password and repo access | Not protected (by design) |
| Malicious/tampered artifact | Fail-closed design goal; validation pending |
| Compromised host or memory access during use | Out of scope |
| Sensitive content inside sessions, or in Git metadata/history | Out of scope; warn users |
| Password loss | Unrecoverable by design |

# SessionPort V1 — Product Specification

> **APPROVED FOR IMPLEMENTATION — NOT FROZEN.**
> The owner approved the V1 baseline on 2026-10-09. PROPOSED/OPEN technical decisions remain gated and are not final. See [decision-log.md](decision-log.md) for authoritative status.

## 1. Product summary

**DECIDED.** SessionPort is a local, single-developer tool/plugin for OpenCode that moves native OpenCode project sessions between environments via Git. Git is **user-operated transport only**: SessionPort never runs Git commands. The user commits, pushes, pulls, and checks out the checkpoint artifact manually (for example on a dedicated branch or in a synced folder).

**DECIDED.** SessionPort is not a sync service, not a collaboration tool, and not a session server.

## 2. Target user and scenarios

**DECIDED.** Individual developer who works across machines or worktrees and wants project session history available elsewhere.

Informative scenarios:

- Continue work from one machine on another through an existing repository.
- Keep session history alongside code, moved by the user.
- Carry sessions into a fresh clone or worktree.
- Move sessions into/out of environments that run OMO Slim (V1: no-op adapter with no OMO-specific transfer — §8).

## 3. Goals and non-goals

Goals (owner-approved V1 intent):

- G1 — Move complete, native session history for the current project through a user-operated Git channel.
- G2 — Safe-by-default restore that never destroys or overwrites local history.
- G3 — Transparent reporting: what a checkpoint included; what a restore did, per session, including partial progress.
- G4 — Mandatory encryption at rest with no plaintext fallback.
- G5 — Capability-based compatibility rather than exact-version coupling.

Non-goals (DECIDED):

- Running Git or any VCS command automatically.
- LLM/model calls, summarization, automatic content transformation, or replay of historical tools.
- Automatic secret detection/redaction (users are warned instead; see security doc).
- Secure deletion guarantees.
- Merging or resolving divergent session content.
- Multi-user/team sharing semantics.
- Portability to editors other than OpenCode.
- Guaranteeing compatibility with every OpenCode version.

### 4.2 `/restore` (behavior DECIDED; details partly OPEN)

1. Prompt for the password (restore permits three failed password attempts per command run — owner decision 2026-10-10; P-13/O-07) and read the artifact.

## 6. Restore semantics

DECIDED, as stated in §4.2. Definition notes:

- "Identical" means exact equality of the complete `{info,messages}` payload compared as canonical JSON with object keys sorted only, preserving all values, array order, IDs, and absent-vs-null (owner-approved 2026-10-09; O-04 resolved).
- Reference remapping applies only to schema-defined session references (`info.id`, `info.parentID`, `info.fork.sessionID`) and message references (message `id`, `info.fork.boundary.messageID`, `info.revert.messageID`); every message ID in every session planned for import is deterministically rederived regardless of destination collision (owner clarification 2026-10-10; not collision-only), with exact duplicate sessions skipped by preflight left unchanged and schema-defined message references following the same mapping; snapshot IDs, `revert.partID`, tool-call, shell, and skill IDs are preserved as distinct/opaque. External references must resolve to an existing destination object during full preflight or the restore fails before any import; remapped IDs are deterministic (stable artifact identity + original ID) so a retry after a partial import reuses the same values, and a collision with a different destination object fails preflight instead of regenerating (owner-approved 2026-10-09; message-ID clarification 2026-10-10; O-05 resolved). The artifact identity/ID-derivation scheme is owner-selected for implementation (2026-10-09, O-22): one random 128-bit artifact identity per checkpoint artifact, authenticated in the artifact; remapped IDs derived with BLAKE2b-256 over a versioned, namespace-separated, unambiguously length-prefixed tuple containing artifact identity and original ID; encoded as `ses_` + 64 lowercase hex for sessions and `msg_` + 64 lowercase hex for messages; the same artifact inputs derive the same output, and distinct checkpoint artifacts are distinct even for identical payloads. Exact authenticated-field placement and framing bytes remain provisional under O-02; runtime validation remains OPEN (OQ-24). E33 adds bounded evidence that two exact-shaped `msg_` IDs and the `ses_` ID read back verbatim through the actual TUI client (one Windows v2.0.22 host; one run) — supplied-ID shape only; no derivation/collision/related-session claim. Source research establishes only `ses`/`msg_` prefix requirements; E27 confirms arbitrary prefix-valid supplied IDs (shorter than the selected 64-hex width) round-trip on one Windows v2.0.22 headless server, with collision behavior bounded as recorded there. Host acceptance of the exact 64-hex supplied-ID shape is bounded-verified by E28 (`fix-30`; one isolated Windows v2.0.22 headless server; 6/6 exact import/read/export checks; supplied IDs only — not SessionPort's BLAKE2b derivation); derived-ID collision handling, related-session/fork references, parent/child/fork cases, cross-platform behavior, plugin-context method availability, and general transactional semantics remain unverified.
- Artifact integrity guard: collapse fully identical repeated session records inside an artifact first (same session ID + exact canonical payload match); after that collapse, message IDs must be unique within and across the remaining unique session records — any duplicate message ID still present among unique records rejects the whole artifact before any import, and divergent records sharing a session ID also reject the artifact. Duplicate message IDs that appeared only because an identical record was repeated are removed by the collapse (owner-approved 2026-10-09; duplicate-policy clarification 2026-10-09; O-04 resolved).
- Corruption policy: corrupt core data → reject before any import (owner decision 2026-10-10; O-11 resolved): fail the entire artifact before any import on any invalid payload/authentication, UTF-8/JSON, schema/root/unknown-field, reference, or planner error; no salvage or partial data. Strict fail-closed policy; no claim that all artifacts are validated at runtime.
- Cross-project collision policy (owner-approved 2026-10-14 source amendment; source-only, fake-tested — no host run): foreign (non-destination) session IDs are occupancy evidence only and never satisfy references, classify exact duplicates, or classify retries; a source ID occupied outside the selected destination is deterministically renamed with the same O-22 derivation; a derived target ID occupied outside the destination but absent from it fails closed; exact planned retries are recognized only in the selected destination; selected-destination exact-duplicate skip and no-overwrite semantics are unchanged. E49 remains failed/unknown-cause; no new host run is authorized (the scoped reopened Gate-3 review `ora-40` returned GO for implementation correctness only — not host-run, release, compatibility, or security approval).

## 7. Compatibility stance

**DECIDED.** Compatibility is checkpoint-format/capability based, not exact OpenCode version equality. SessionPort feature-detects the required import method and fails safely before writes if it is unavailable. V1 policy (owner decision 2026-10-10 — O-12): at `/restore` start, check whether `context.client.session.import` is callable before reading or decrypting the artifact; if absent, show a clear message that the required capability is unavailable and no sessions were changed, then stop. The installed context surface is bounded-verified on one actual TUI host — the earlier O-19 smoke attempt produced no runtime result (E30, historical); the later bounded O-19 probe (E32, `fix-47`) established plugin setup and `sodium.ready` in one Windows v2.0.22 TUI plugin setup runtime but made no `context.client` calls; the subsequent bounded actual-TUI client probe (E33, `fix-49`) verified `typeof ctx.client.session.import === 'function'`, callable `session.get`/`message.list`, and exactly one synthetic public-client import with an explicit target succeeding and reading back (one run, no retry) — so broader versions/platforms, the concrete product probe implementation, and any product fail-early behavior remain OPEN (OQ-12; not implemented); E1's declaration mismatch is bounded-addressed at runtime on that one host only. Baseline: OpenCode **v2.0.22 (2026-10-09)** — an evidence baseline only, not a support promise.

**PROPOSED.** Over time, maintain a tested-support matrix; unknown versions are allowed only when required capabilities are detected as present and the artifact format version is supported.

## 8. OMO Slim adapter (V1 no-op)

**DECIDED (P-14, 2026-10-09).** In V1, OMO Slim support is a no-op: native OpenCode sessions are the only payload and there is no OMO-specific data transfer. SessionPort never inspects or copies OMO configuration, credentials, agent/tool definitions, or host-managed state, and never scrapes private job-board/session internals; static package/config presence is not capability evidence. The optional adapter is reconsidered only if a documented public, stable, versioned OMO export/import API appears (O-13 resolved for V1). This decision does not extend owner approval to config reading or scraping.

## 10. Security posture (summary)

Mandatory password encryption; compression before encryption; password never stored with the artifact or repository; password loss is unrecoverable; no plaintext fallback and no plaintext temp-file design; decrypted material stays in memory within bounded limits; no secure-deletion promise. Password-entry UI research (E34, 2026-10-10): official OpenTUI 0.5.14 input has no mask mode and renders its real value, and the Solid reconciler debug logger may include plaintext text-node values when DEBUG is enabled; a prototype exists but its only tests are state-flow unit tests (no runtime leakage test had run at the time of E36); a follow-up testability lane (E36, 2026-10-10) found no reliable component/test-renderer leakage test is currently established (OpenTUI `testRender` under Bun's normal test condition rendered the modal but its `useKeyboard` hook did not subscribe — mock key input only reached OpenTUI's Ctrl-C handler; a browser-condition run captured frames that did not update consistently; the incomplete test was removed) — the final suite is state/API compile evidence only (`bun test tests/tui/ui`: 9 state-flow tests/31 expectations; `bun run typecheck` passes); a later bounded actual-host probe (E41, 2026-10-10; `fix-69`: four runs — two clean with DEBUG off/on and two disclosed development runs; input injection and frame/log capture completed; all four reported target cases exercised but not enumerated; zero raw-secret hits across captured frames, stdout/stderr, console cache, saved DEBUG log, and a full-root file scan; SHA-256 byte equality between typed/pasted secrets and accepted bytes; baseline restored, temp artifacts/root cleaned, repository untouched) supersedes the prior current-status statement that no host leakage/input probe had run; O-07 remains OPEN only for exact case-level coverage, clipboard-write behavior, product integration, and lifecycle requirements not explicitly established, and actual TUI input, frame, event/log, and DEBUG-on/off tests remain OPEN for those residuals (the report specifies no exact host/runtime versions); bounded observations only — not a general host guarantee, secure-memory-erasure claim, complete product integration, cross-version/platform/support claim, or broad security validation. Full detail and caveats: [security-and-privacy.md](security-and-privacy.md). Exact cryptography remains OPEN. PROPOSED/recommended and authorized for implementation/validation (not approved as a final design): pinned `libsodium-wrappers-sumo@0.8.4` (JS builds embed ~285 KB WASM and instantiate it; no standalone `.wasm`; corrected 2026-10-10 by E35) with libsodium Argon2id password KDF and XChaCha20-Poly1305 `secretstream` over a streaming-gzip payload, versioned envelope with an allow-listed Argon2id profile and explicit algorithm identifiers, no silent KDF/cipher fallback. Profile read semantics are owner-approved (2026-10-09 — T-10): `create(policy)` selects the sealing profile, and opening may use any profile in the explicitly supplied allow-list, with unknown profile codes rejected before KDF; the runtime policy registry is intentionally empty and no production profile or parameter values are selected. Phase 1 synthetic primitive tests and Phase 2 provisional-container unit tests passed under Bun 1.3.10/Windows (see [validation-and-open-questions.md](validation-and-open-questions.md), E19/E20), including error-path best-effort clearing tests; the reviewed unexpected-tag cleanup issue is closed (Oracle `ora-17` GO for that issue specifically; fix-19 fail-before/pass-after regression evidence), which is not overall crypto design or Gate 2 approval — strict end-of-input validation host-runtime verification (E22/E23/E26; the decoder is owner-selected — `pako@3.0.2`, T-11 — with implementation complete/tested `fix-25` and Oracle `ora-22` GO scoped to implementation correctness only; host-runtime validation not performed), KDF blocking, packaging, production profiles/caps, memory, and format freeze remain OPEN. The gzip member boundary policy is owner-decided (2026-10-09): accept one or more complete gzip members and reject any bytes after the final member, including zero padding; strict end-of-input validation is required before plaintext is released;

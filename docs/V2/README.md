## 3. Architecture snapshot (local source vs proposed)

- **Local plugin (existing):** `src/core/**` (collector, dependency closure, crypto container, restore planner, identity derivation) and `src/tui/**` (commands, adapters, orchestration).
- **Local cloud client seam (unwired):** `src/cloud/auth` (native device client + credential port) and `src/cloud/vault` (injectable keyring adapter); intentionally not wired into the TUI. `src/cloud/{crypto,state,sync,host}` remain proposed and are not created.
- **Cloud API (local source):** `cloud/api` — one Fastify (Node + TypeScript) service with Prisma + PostgreSQL, health-only by default; cloud mode composes the project/revision/me routes, nine native-auth methods, and four BetterAuth browser routes. No deployment, application DB, enabled production auth, storage/upload mount, or runtime acceptance.
- **Cloud web (local source):** `cloud/web` — Next.js App Router thin adapters over a Feature-Sliced Design tree (`_app/_pages/widgets/features/entities/shared`) for login, device approval, and connected devices; no dashboard and no real OAuth/backend acceptance.
- **Storage:** a private S3-compatible bucket is selected (Beget); Post Policy + conditional-copy capability is **not yet proven**, and M4 upload/download remains unmounted and fail-closed with no fallback.
- **Repository mechanics:** `cloud/api` and `cloud/web` as npm workspaces while Bun remains the root plugin toolchain; the plugin's published pack allowlist is preserved (cloud code is excluded from the plugin tarball).
- **No extra infrastructure:** no Redis, no queue/worker tier, no WebSockets, no Kubernetes — the janitor/finalization run inside the API process under database locks.
- **E2EE:** session content is sealed client-side with the existing crypto container; for session content the server sees only opaque IDs, sizes, and ciphertext hashes. The sync passphrase wraps a random account root; the server never receives session plaintext, the sync passphrase, or unwrapped encryption keys. Authentication credentials are handled by the authoritative auth service (GitHub account and device/grant records) and are not covered by this E2EE assertion.

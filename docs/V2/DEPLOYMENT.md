## 4. PostgreSQL (existing VPS instance)

- One existing PostgreSQL server is reused. **No second database container** is planned or required.
- Separate database `sessionport`, with **two roles**:
  - **runtime role** (`sessionport_app`): least-privilege DML on the application schema only; used by the API at runtime; no DDL.
  - **migration role** (`sessionport_migrator`): DDL/migrations only; used by one-off migration runs; never configured into the API runtime.
- BetterAuth owns its own auth tables in the same database and applies its own vendor migrations (pinned and validated in AUTH-01; [SECURITY.md](SECURITY.md) §6). Business tables are Prisma-owned ([API_AND_DATA.md](API_AND_DATA.md) §6). Vendor schemas are never hand-rolled or inferred.
- Connectivity when the API runs in a container on the VPS host (planned compose deployment):
  - Use an **explicit host-gateway alias** (illustrative: an `extra_hosts` mapping such as `db-host:host-gateway`) or an equally explicit host address. **Never `localhost`/`127.0.0.1` from inside the container** — that addresses the container itself, not the host PostgreSQL (the classic mismatch).
  - `pg_hba.conf` (Linux): restrict the API's source to the specific Docker bridge subnet/address and require **SCRAM** authentication; no `trust`.
  - Bind `listen_addresses` to the specific interface(s). **PostgreSQL is never exposed publicly.** A broad `0.0.0.0` listen wildcard is not used unless the execution task records why it is required and what constrains it.
  - Illustrative only (not executed):
    ```conf
    # pg_hba.conf excerpt (illustrative)
    host  sessionport  sessionport_app  <docker-bridge-cidr>  scram-sha-256
    ```
- Connection strings are server-side secrets (§8); TLS requirements follow the VPS's existing PostgreSQL configuration.

## 6. Web BFF (Vercel)

- `cloud/web` is a thin same-origin BFF. It holds no business logic and no session data.
- Canonical issuer: `https://<APP_ORIGIN>/api/auth`. `/api/auth/*` is forwarded to the Fastify API while preserving the trusted canonical origin; the GitHub OAuth callback is registered at the web BFF ([SECURITY.md](SECURITY.md) §6; [API_AND_DATA.md](API_AND_DATA.md) §3).
- Forwarding is **allowlisted**: only the documented auth routes and required headers; the API origin is static configuration (no user-controlled upstream — no open proxy). Provider secrets and the BetterAuth secret are server-only and never shipped to the browser.
- **Two verified principals only** ([API_AND_DATA.md](API_AND_DATA.md) §1): plugin clients use a bearer device token checked against an active bound device/grant on every request; the browser dashboard uses a cookie session forwarded through the allowlisted same-origin BFF and validated at the API itself (active user plus CSRF/origin checks). The browser never holds or fabricates a device bearer token, and the BFF cannot assert an arbitrary user header.
- Browser sessions: `HttpOnly`, `Secure`, `SameSite=Lax` cookies served via the same-origin BFF; CSRF protection uses origin/token checks and provider `state`; no wildcard CORS; no cross-origin auth cookie.
- Trusted proxy: the BFF/edge sits in front of the API, so the API honors forwarding headers (host/proto) only from the known proxy. If a shared proxy secret is chosen, label it as a SessionPort configuration value mapped by an adapter — not as a library built-in variable name.
- Revocation limits to document for users: revocation denies API access immediately, but an already-issued presigned download URL remains valid until its short expiry (5 minutes candidate; [SECURITY.md](SECURITY.md) §6–§7).

## 9. Migrations


## 10. Rollout and rollback

- Order: (1) database expand/migrate, (2) API deploy, (3) website/BFF deploy, (4) clients opt in (sync stays opt-in; local commands are unaffected).
- Gates: `/health/ready` must pass before traffic is routed; uploads stay disabled until STORE-01; auth stays feature-gated until AUTH-01; no cloud native import or update occurs before HOST-01 passes.
- Rollback: roll back the API/web deployment to the previous immutable image. Schema changes must remain **forward-compatible**; do not reverse destructive migrations, and never delete data as a rollback step.
- Cloud operations never replay native tools and never write native sessions outside the HOST-01-gated path ([SYNC_PROTOCOL.md](SYNC_PROTOCOL.md) §12).
- After a restore or rollback, re-check device revocation state so a restored environment does not resurrect revoked devices (§11).
- Clients tolerate an older/newer API within the `/v1` contract; during transitions the documented status semantics apply — `422 INVALID_CURSOR` for malformed cursor values or values beyond the established `upperBound` (no retention-based cursor expiration; all committed revisions are retained) and `410 upload-expired` for an expired upload reservation ([SYNC_PROTOCOL.md](SYNC_PROTOCOL.md) §5.2, [API_AND_DATA.md](API_AND_DATA.md) §1).

## 11. Backups and recovery

- Back up metadata (PostgreSQL) and object storage **together**; backups are encrypted at rest in the backup target. Key wrappers may be included (they are opaque); the account root and sync passphrase never are.
- Object-store lifecycle applies only to staging objects and explicitly fenced orphan keys — there is **no blanket final-prefix expiry**, and a final object referenced by a committed revision is never lifecycle-deleted. Unattached `ready` uploads past the 24 h candidate grace TTL are janitor-GC'd, with `usedBytes` decremented only after confirmed deletion ([API_AND_DATA.md](API_AND_DATA.md) §7).
- Restore drill: restore database + storage, then verify (a) auth and revocation paths work and revoked devices stay revoked, (b) quota counters match actual objects, (c) no plaintext session content is accessible to the operator. Record drill results as evidence.
- Credential rotation: database roles, S3 keys, GitHub client secret, and the BetterAuth secret. The rotation procedure is an OPS-02 item.

## 12. Monitoring (sanitized only)

- Metrics/logs may include: auth failures/denials, active device counts, outbox staleness (aggregate only, if implemented), quota usage near limits, janitor/S3 cleanup counts, health and latency.
- **Never**: session content, content digests, plaintext names/paths, tokens, or keys.
- Alert candidates: `/health/ready` failing, auth error spikes, janitor failures, quota near-limit, storage capacity.

## 13. S3 provider requirements (STORE-01)

- Required provider capability before uploads are enabled: Post Policy with exact content-length range + SHA-256 checksum; HEAD validation; ETag-conditioned server-side copy to an immutable final key **unique per (upload, lease generation)** so a stale finalizer can only write its own orphan, never the winning object; final HEAD; versioning off for staging; lifecycle cleanup restricted to staging and explicitly fenced orphan keys (1-day candidate) — **never a blanket final-prefix expiry**, and committed final objects are never lifecycle-deleted; janitor deletion of only unreferenced terminal/fenced keys.
- **No weaker fallback**: a provider lacking any required capability blocks uploads rather than silently degrading ([SECURITY.md](SECURITY.md) §7).
- Cost note: staging/copy physical overhead is transient and excluded from the user's logical quota; it is bounded by outstanding-reservation limits and rate limits. This is **not** a strict "all bucket bytes are accounted" guarantee ([API_AND_DATA.md](API_AND_DATA.md) §7).
